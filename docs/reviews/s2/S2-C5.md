## Open questions for the owner

1. **A new requirement starts at `version` 2.** Create inserts the row, then revision 1, then
   sets `current_revision_id` through the ORM (the foreign keys are circular and not
   deferrable), and that update counts as a version bump; every other versioned row starts at 1.
   Nothing depends on the starting number (a client sends back the version it read), and the docs
   don't name one. Options: (a) accept 2 and say so in the schema doc; (b) write
   `current_revision_id` with `direct_update` (no bump), widening backend `CLAUDE.md`'s list of
   what may bypass optimistic locking; (c) make the foreign key deferrable (a migration) and insert
   both rows with the pointer set. Recommendation: (a), the smallest; (c) only if a starting
   version of 1 matters to you.
2. **An item level below the project's at creation.** Design-doc §3.1 says items "can raise the
   level …, never go below the project's"; create accepts `internal` on a `confidential` project
   and stores it, while the effective level stays `confidential`. Options: (a) accept: the
   stored level is the item's own, and "never below" means in effect (the schema doc's wording),
   with the S2-C18 badge showing the effective level; (b) refuse a stored level below the
   project's with a 422 (S2-C6's restriction PUT the same). Recommendation: (a): lowering the
   project later would otherwise leave items whose stored level was refused, and the effective
   rule already holds.

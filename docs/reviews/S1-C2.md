## Proof the tests can fail (sabotage checks)

| Sabotage | Caught by |
|---|---|
| A read-then-write allocator (`SELECT next_value`, then `INSERT` or `UPDATE`) | the three race tests: never collide, never collide on a fresh counter, same prefix waits (the sequential tests still pass: the bug only shows under concurrency) |
| Allocation locks the whole project row (`SELECT … FOR UPDATE`) | `test_an_open_allocation_doesnt_block_another_prefix`, `…_doesnt_block_editing_the_project` |
| No start barrier in `run_in_parallel` | `test_every_transaction_starts_before_any_work_runs`, 3 runs of 3 |
| No time limit on the parallel section | `test_a_parallel_section_that_runs_too_long_fails` |
| No `lock_timeout` on the concurrency engine | `test_connections_have_a_lock_timeout` |
| The `concurrency` fixture doesn't run the empty-tables check | `test_a_test_that_leaves_rows_behind_errors_and_its_rows_are_removed` (runs a leaky test in its own pytest process) |
| The upsert doesn't set `updated_at` (after review) | `test_an_allocation_moves_the_counters_updated_at` |

While writing the wiring test, its first version leaked a row into `audit_event`, which the
fixture's `TRUNCATE workspace CASCADE` already empties (it references `workspace`): the test
passed for the wrong reason. It now leaks into `user`, which that cascade doesn't reach; the
developer guide notes that truncation cascades along foreign keys.

**Questions raised**

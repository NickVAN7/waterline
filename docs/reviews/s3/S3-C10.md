- **The owner's three answers** (Nov 25, 2026, before building; DL-414, design-doc §6): coverage
  leaves cancelled tasks out (and `has_tasks` with it); the approval states are independent
  facts; the requirement's tasks are the backlog's rows (`TaskList`), subtasks read per task.
- **No spec tests:** no action or rule changed (the build plan's list doesn't name S3-C10); the
  tasks read is `requirement.view` on the requirement, then `task.view` on the project, as the
  plan's actions table says. Its 404 and export-control cases are the main session's, marked
  `security`.
- **The tree is a `ListSpec`** (`TREE`, `paging="ranked"`, through `fetch_ranked`), with no
  sorts and `sort_first=(rank,)`; `ListSpec.query_model` now offers `sort` only when a spec has
  sorts (every offset and ranked spec but the tree has some, so no other API changes). The two
  filters on other tables are `EXISTS` expressions in the requirement repository (`HAS_TASKS`,
  `AWAITING_APPROVAL`, and `with_approval_state` for the `CustomFilter`).
- **Context ancestors are added for every match**, filtered or not: an unfiltered tree's matches
  are every requirement, so none is missing unless the tree is truncated, when a match's parent
  past the cap now comes as context too.
- **The tasks read lives in the task area** (`TaskService.for_requirement`, the task router),
  loading the requirement through `load_requirement` with `requirement.view`.

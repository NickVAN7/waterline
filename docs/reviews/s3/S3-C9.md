## Decisions during the checkpoint

- **Backend only** (owner, Nov 25, 2026): the Trash page isn't taught task rows in this row; it
  gains only the `task` label its type map now requires. Its task rows show as requirements and
  restore through the requirement endpoint until S3-C20 (TD-133).
- **The trash is one union** (plan fix F6): each table gives a part selecting `type`, `id`,
  `deleted_at` (`RequirementRepository.trash_rows`, `TaskRepository.trash_rows`);
  `RequirementRepository.trash()` unions them into one subquery, and `TRASH` declares its
  sort and filter on unqualified columns (`TRASH_TYPE`, `TRASH_ID`, `TRASH_DELETED_AT`) that name
  that subquery's columns, so `fetch_page` pages, counts, sorts, and filters it unchanged. The
  page's IDs are then loaded from both tables; a row restored since the page was read is left
  out.
- **Raising a restored item to its project's level** is one helper, `lift_restored()` in
  `app/services/project.py`, beside `lift_items()`; the requirement restore uses it too (it had
  the same lines inline).
- **Delete and restore lock like an edit:** the project held, then the task's row, then
  `task.delete` / `task.restore` checked again on the locked row (an archive or a reporter
  change that committed meanwhile takes the right away); a restore finding `deleted_at` already
  cleared is a 404. A restore keeps the task's rank, so it comes back in its place.

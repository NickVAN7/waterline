## security-reviewer, pass 1 (base `bc433c7`) — verdict: ready after fixes

| # | Severity | Category | Finding | Resolution |
|---|---|---|---|---|
| 1 | major | authz | **The content/management marking defaulted to management, the open side** (`app/authz/actions.py`, `ActionSpec.access`). No action set it, and the spec test only saw the default, so a Slice 2 content action registered without `access=CONTENT` would silently pass the export-control gate for every inherited admin (design-doc §3.1, §5: the registry marks every action, and `authorize()` fails closed). Fix: no default, or default to content. | Fixed: the default is now `CONTENT`, and all 21 registry entries state `access=AccessKind.MANAGEMENT`. `test_every_action_so_far_is_marked_management` now checks real markings; sabotage-checked by marking one action content (caught). Making the field required would have changed two spec-test files' test-only actions, so the closed default was chosen instead. |
| 2 | minor | tests | **The export-control confirmation tests weren't marked `security`** (`tests/api/test_project_classification.py`), so `-m security` runs left out the main control on who joins an export-controlled project. | Fixed: `pytest.mark.security` added to the file's `pytestmark`. |

**Questions raised** (for the owner):
- (Answered: **owner decision**, chat, Oct 12, 2026: "it should update the admin role". Built:
  `set_classification` re-reads the caller's project role under the lock (`_with_current_role`),
  with `test_an_explicit_admin_removed_while_their_change_waits_cannot_remove_export_control`,

The `AuthzContext` is loaded at the start of the request, and `set_classification` checks rights against it after waiting on the project lock. Should the explicit-admin check for `project.lower_classification` re-read the actor's membership under the lock, or is this an accepted risk (tech debt)?
